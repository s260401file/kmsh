一、開場演練（會前模擬）

演練情境

  • 模擬 20 戶 / 10 人出席 的最小可投票情境
  • 透過後台「報到清單」介面，直接點選綁定委託（A01 ↔ A04、56P ↔ A04 等）
  • 多戶綁定一人的情境亦進行測試

流程確認

  • 報到時可從後台直接做委託綁定，現場彈性高
  • 手機畫面（住戶端）目前不會顯示控制細節，僅由後台操作

三、議案 / 臨時動議流程爭議（本次會議核心議題）

3.1 「下一單元」命名問題

  • 現況按鈕：「下一單元」
  • 問題：現場長輩看不懂「單元」是什麼意思
  • 共識：改為 「下一程式」 或 「下一步驟」（會議「程式」是傳統會議用語）

3.2 議題討論（Step 6） vs 臨時動議（Step 7） 性質差異

特性Step 6 議題討論Step 7 臨時動議
議案來源會前公告，由住戶提案 → 管委會審核留下合規者現場即時提出
順序可否調動可以（重大議案人數不足時可移到後段）不可以（必須一個一個處理）
是否可擱置可以（先放著等人多再議）必須當下表決，有人附議就必走完表決

3.3 校長強烈主張：臨時動議不可跳來跳去

「臨時動議並非無限度的一個接一個處理，而是必須遵守一次一個動議的方式，當前的動議沒有處理完成之前，不得提出新的主動議。」
  • 現場若爭議過大，主席可宣布「等想清楚再提」，但不能新增第二個臨時動議
  • 目前系統允許 Step 7 連續新增多個臨時動議的設計不符合議事規則

3.4 程式跳轉 recheck 機制

  • 議案還沒討論完 → 主席誤點「下一程式」進入臨時動議
  • 建議：在 Step 6 → Step 7 切換時加入 confirm 提示「您還有第 N 個議案未討論，確定要進入臨時動議？」
  • 跳過議案的合法情境：重大議案三分之二門檻未達 → 主席宣布列為下次會議討論

3.5 「下一程式」按鈕無條件 recheck

  • 共識：每次進入下一程式都加 recheck（與其逐個情境判斷，不如全部都檢查）

四、議案結果狀態擴充

現況

僅有 通過 / 不通過 兩種結果。

需新增的狀態

狀態說明觸發情境
作廢議案議案違法、不可討論臨時動議中提出重大議案、社區規約調整等不可在臨時動議討論的事項
擱置議案有表決但無結果 / 暫不表決第一輪投票各選項都未達二分之一；或主席決定先擱置改下次再討論

多選項議案的二分之一處理（一般中華醫院案例）

  • 情境：四個選項，最高票未達二分之一（法定門檻）
  • 建議流程：
    1. 第一輪：四選項普通投票
    2. 若無人過半 → 取最高票兩個 → 第二輪二選一
    3. 確保最終達到法定二分之一
  • 此邏輯應作為「進階表決選項」加入

表決遊戲規則差異

  • 不同社區規則不同：絕對二分之一 vs 相對多數
  • 共識：結果讓使用者自行認定 —— 系統呈現得票數與百分比，由主席現場裁示判定

五、AI 整合方向討論

5.1 已達共識的部分

AI 不可介入 的部分：

  • 議題討論結果
  • 臨時動議結果
  • 委員選舉結果
  • 理由：這些是現場票數產生的決議，AI 判斷可能與現場不一致，造成天下大亂

AI 可協助 的部分：

  • 全程錄影 / 錄音 → 語音轉文字
  • 自動產生會議紀錄草稿（主席報告、宣讀上次會議紀錄、報告事項等敘述性內容）
  • 總幹事仍需審視修改

5.2 會議紀錄的雙軌設計

來源內容
系統現場產生（不可改）議題討論結果、臨時動議結果、委員選舉結果
AI 輔助產生（可由總幹事修改）主席報告、上次會議紀錄宣讀、報告事項等

5.3 數位主席（概念性，10-20 年後）

  • 校長提出：未來可由 AI 主席代理（很多人不想當主席因為容易被告）
  • 結論：屬於概念產品，目前補助案不適合，但可作為長期路線

5.4 不記名投票討論

  • 公會選舉建議使用不記名（一般大選都不記名）
  • 議題討論建議記名（方便日後法院取證）
  • 系統現況：每張票可追蹤投給誰
  • 待規劃：不記名模式的票軌設計

AI 亮點設計考量

  • 評審看「AI 是否提供實際幫助」，而非「為了 AI 而 AI」
  • 數位主席太前衛 → 落不了地 → 補助案不適合
  • 會議紀錄自動產生 → 對總幹事有實際幫助 → 適合作為亮點
  • 三因子身份驗證（手機 + 身分證 + 鍵盤卡）可作為另一個亮點

成本估算（AI Token）

  • 兩小時會議的轉錄 token 數量不會太誇張
  • 可考慮 自建 LLM 主機 攤平成本（如月攤一千場會議 → 每場成本可控）
  • 自建主機亦可降低「資料受 OpenAI / Anthropic 等第三方掌控」的風險

缺口 8：多選項議案「二輪二選一」邏輯

現況：議案支援多選項投票，但無「無人過半 → 取最高兩項再表決」自動引導。

建議實作：

  • 開票後若無選項達門檻（如二分之一）：
    • 系統提示「無選項達門檻，是否進入第二輪表決？」
    • 確認後自動以最高票兩個選項作為新議案進入第二輪
  • 此邏輯可作為「進階表決」的選項，由主席於建立議案時選擇是否啟用

缺口 9：AI 會議紀錄輔助（新增模組）

現況：系統無語音轉文字或 AI 生成功能。

建議實作（分階段）：

  • 階段 1：錄音/錄影上傳 + 第三方 API（如 Whisper）語音轉文字
  • 階段 2：將轉錄稿 + 系統已有的決議結果（議案、臨時動議、選舉）合併，由 LLM 生成會議紀錄草稿
  • 階段 3：自建 LLM 主機（補助通過後執行）
  • 重要原則：結果類資料（決議、票數）必須以系統現場資料為準，AI 不得修改

缺口 10：不記名投票（票軌設計）

現況：投票紀錄可追蹤至個人（VoteLock 表 + 投票記錄表）。

建議實作：

  • 議案 / 選舉建立時新增「投票模式」欄位：
    • 0 = 記名投票（預設，議題討論用）
    • 1 = 不記名投票（委員選舉用）
  • 不記名模式：後端只記錄「該票投給誰」，不記錄「誰投了這票」
  • 仍保留 VoteLock 防止重複投票，但 vote 表與 voter 解綁
